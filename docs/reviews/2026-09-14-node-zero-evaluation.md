# Node 0 실제 생성 평가와 중심 질문 보존

## 범위와 방법

기존 `eval/start.jsonl` 17건 중 REFRAME_NEEDED인 ST-06~ST-16 11건을 실제 Node 0 런타임으로 호출했다. fixture와 정답은 변경하지 않았다. Sol high, 출력 상한 2048, 배치당 최대 11회, SDK 재시도 0회다. 사용자 실제 입력은 평가 로그에 사용하지 않는다.

새 평가기는 출력 schema·원문 인용·금지어를 검사한다. 질문과 근거 설명의 금지어를 함께 검사하며, 자동 통과가 의미 적합성을 보장하지 않으므로 보고서의 `semanticReview`는 `PENDING`으로 남긴다. 아래 문구 검토는 Codex의 별도 검토이며 사용자 승인이나 독립 사람 평가가 아니다. 승인 전 Node 저장 금지 등 앱 흐름은 변경하지 않았다.

11회 완주, 자동 검사 통과. 입력 6125·출력 2423 tokens. 그러나 ST-06~09, ST-15~16은 선택·판단 고민을 망설이는 이유에 대한 후속 질문으로 바꿨다. ST-14는 이직하고 싶은 이유 대신 그 이유를 모르는 이유를 묻는 중첩 질문이 됐다. ST-10은 아직 써 달라고 한 메일을 이미 쓴 메일로 표현했다. 자동 검사만으로 이 문제들을 잡지 못했다.

## 수정

`node-zero-v2-2026-09-14`는 RULES의 첫 중심 질문과 REFLECT 역할 구분을 명확히 한다. 선택 여부·판단의 대상을 최소한으로 재구성하고, 단순한 망설임을 이유나 판단 방법 질문으로 치환하지 않는다. 이유 자체가 명시된 고민이면 원래 대상의 이유를 묻고, 사실·시제를 보존한다. 개별 fixture 정답을 prompt에 삽입하지 않았다. Safety·Start classifier·Judge와 공통 어댑터는 이번 수정에서 변경하지 않았다.

## 남은 검증

이 11건은 개발에 사용한 기존 사례이며 holdout이 아니다. 다중 초점 선택 뒤 생성, 추가 경계 입력, 실제 로그인→입력→승인→DB 저장 및 조회는 별도 검증이 필요하다. 운영 모델/reasoning이나 익명 공개 범위를 이 결과만으로 확정하지 않는다. 일반 대화의 Judge→C/D→저장 연결도 별도 구현이다.

사용자는 Google 로그인 후 localhost 복귀 문제를 해결했다고 알렸고 브랜딩 작업은 별도로 진행하기로 했다. 이는 운영 전체 경로를 독립 검증했다는 뜻이 아니다. 이 작업에서 운영 환경변수·DB·Vercel 배포·PR 병합은 변경하지 않았다.
