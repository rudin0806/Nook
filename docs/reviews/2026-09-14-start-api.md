# 첫 입력·초점 선택·승인 API 연결

기준: PR #2 `4a6c5f6`, 2026-09-14. 제품 의미와 Safety 정답은 변경하지 않았다.

## 운영 이력 확인과 적용

- 원격 `ai_request_admission`은 `20260914090858`, `approve_start_question`은 `20260914090912`로 이미 적용되어 있었다. 재적용하지 않았다.
- 로컬 파일 `20260914090000` / `20260914090144`와 각각 대응한다.
- 이번 `20260914092155_start_api_persistence.sql`은 원격 `20260914093022`로 적용했다. 기존 테이블/정책/데이터를 바꾸지 않고 서버 전용 저장 함수 두 개를 추가했다.
- `commit_start_input`: 첫 Session/Segment 및 허용된 Message 생성, 필요 시 Safety 종료, 요청 성공 기록을 한 트랜잭션으로 묶는다.
- `terminate_start_approval`: 수정된 승인문이 STOP/HANDOFF일 때 원자적으로 종료한다. STOP 원문은 SQL 인자에도 전달하지 않으며 HANDOFF는 Message를 저장한다.
- 두 함수 모두 anon/authenticated 실행 권한 없음. 서버에서 인증한 user ID만 전달하며 소유권·요청 lease·만료·첫 노드 상태를 DB에서 재검사한다.
- 원격 `supabase/tests/start_api.sql` 전체가 오류 없이 실행됐고 마지막 ROLLBACK으로 테스트 계정과 데이터를 제거했다.
- Security Advisor는 전후 동일: [기존 authenticated SECURITY DEFINER 경고 9건](https://supabase.com/docs/guides/database/database-linter?lint=0029_authenticated_security_definer_function_executable), [서버 전용 요청 테이블의 RLS 정책 없음 정보 2건](https://supabase.com/docs/guides/database/database-linter?lint=0008_rls_enabled_no_policy). 새로운 공개 함수 경고 없음.

## HTTP 계약

모든 경로는 POST, JSON, 서버 설정 `NOOK_SITE_URL`과 같은 Origin, 검증된 Supabase 쿠키 사용. body의 user_id나 모델 설정은 허용하지 않는다. 최대 64 KiB를 스트림으로 제한한다. 기존 보관 API의 기본 8 KiB 제한은 유지한다.

| 경로                 | 입력                                    | 결과                                                      |
| -------------------- | --------------------------------------- | --------------------------------------------------------- |
| `/api/start`         | requestId, thought, 선택적 captchaToken | Safety → A → 필요한 경우 Node 0 → 저장 → 제안 서명        |
| `/api/start/focus`   | requestId, receipt, index               | 서명된 후보의 명시 선택 → 소유권 → Safety → Node 0 → 저장 |
| `/api/start/approve` | requestId, receipt, finalText           | 서명·소유권 → 수정문이면 Safety → 승인 Node 원자적 저장   |

- 인증된 일반/익명 사용자는 기존 ID를 유지한다. 신규 익명 생성은 기존 enable 설정과 Supabase에서 검증하는 CAPTCHA가 필요하다.
- 분당 5회·UTC 일당 50회·동시 1건을 기존 DB ledger로 적용한다. 첫 입력·초점 선택·승인은 각각 논리 요청이다. 모델 자동 재시도는 없다.
- 중복 요청은 모델과 저장을 반복하지 않는다. RUNNING=202, BUSY/RATE_LIMITED=429 및 Retry-After, CONFLICT/FAILED=409, 성공=200. 응답은 no-store다.
- 후보/미승인 Node는 저장하지 않는다. 서명 토큰은 암호화가 아니므로 본문에서만 전달하며 URL·로그·브라우저 영구 저장소에 넣지 않는다.
- 첫 입력/초점 선택의 성공 응답을 잃으면 동일 요청 재전송은 완료된 Session ID만 돌려준다. 저장하지 않은 후보·서명은 복원되지 않는다. 새 모델 호출을 자동으로 하거나 질문이 승인됐다고 표시하면 안 된다. 재개 UX는 후속 작업이다.
- 승인 재전송은 기존 Node 참조를 반환한다. Safety 종료 승인 재전송은 Session 참조임을 구분한다.
- 여러 고민의 자유 입력 답변 해석은 추가하지 않았다. 확정된 명시 후보 선택만 연결했다.

## 검증

- 단위/HTTP 계약 테스트 103개 통과.
- migration 8개 독립 PGlite 재현 및 SQL 테스트 5개 통과(삭제 연쇄·만료·RLS·시작 API·승인).
- 운영 DB에서 시작 API SQL 검증 통과(테스트 트랜잭션 rollback).
- typecheck / lint / production build 통과. 변경 파일 formatting 통과. 전체 `format:check`는 기존 파일 5개(docs/EVALSET.md, proposals 3개, tests/admission.test.mts)의 formatting 경고로 실패하며 이번 범위에서 수정하지 않았다.
- 실제 production 서버를 로컬에서 실행해 세 경로의 비활성화 응답 및 cross-origin 거절 6개 통과.
- `npm run eval:validate` 직접 실행: judge 32 / start 17 / safety 15, mappedSafety 15, issues 0. 기존 STATUS/PR 본문의 8/10건 실패 기록과 달리 실제 기준 커밋 파일은 정적 검사를 통과한다. 이번 작업은 fixture나 정답을 바꾸지 않았다.
- 실제 Safety/Start 모델 호출, Google OAuth→실제 모델→저장 전체 HTTP 왕복은 실행하지 않았다. 위 테스트가 실제 모델 품질 평가를 대체하지 않는다.

## 운영 공개 전 남은 것

공개 호출은 `NOOK_START_API_ENABLED=true`일 때만 가능하다. 현재 운영 활성화와 새 Vercel 배포는 하지 않았다. 환경변수 값은 조회하지 않았으며 설정 존재/유효성도 아직 확인하지 못했다. 기존 Vercel 운영 배포는 READY로 확인했지만 이 API 코드가 배포됐다는 뜻은 아니다.

`.env.example`의 HMAC 비밀값, Safety/A/Node 0별 모델·추론 수준·출력 상한을 명시적으로 설정해야 한다. 암묵적 운영 모델 선택은 없다. Safety/Start 실제 평가, 기존 Safety 의미·문구 미결 확인, 인증 왕복 검증 후 활성화한다. 입력 화면의 디자인과 버튼 연결, Judge→C/D→후속 대화 저장은 이번 API 작업에 포함하지 않았다.
