## 0. 정의

### 서비스명
**Nook** — 구석진 아늑한 자리, 뭔가를 잠시 넣어두는 공간.

> **Nook**
> 답을 주는 대신, 내가 어떤 질문을 지나왔는지.

이름이 의미를 전부 짊어지지 않는다. 태그라인이 채운다.

### 제품 카테고리
AI 저널도, AI 상담도, AI 마인드맵도 아니다. 각각으로 부르는 순간 Rosebud, Wysa, Xmind와 정면으로 붙는다.

내부 포지션은 **Personal Thinking Tool** — 대화를 통해 내 생각의 현재 위치를 찾고, 그 이동 경로를 남기는 개인 사고 도구.

### 사용자에게 보이는 언어
> 머릿속에 걸리는 게 있나요?
> 정리하지 말고 생각나는 대로 적어주세요.

첫 화면에서 "답을 주지 않습니다"라고 선언하지 않는다. 사용자는 "내 질문이 흐릿하다"고 생각하며 들어오지 않는다. "이거 어떡하지" 상태로 들어와서, 나갈 때 **"아, 내가 사실 이걸 고민하고 있었구나"**를 체감한다.

## 1. 문제

### 출발점
정보가 부족해서 생기는 문제가 아니다. 오히려 **정보가 너무 많아서** 생긴다. 검색하면 수십 개 의견이 나오고 AI에 물으면 또 하나의 답이 나오는데, 그럴수록 "그래서 나는 뭘 원하는데"가 흐려진다.

### 두 가지 페인포인트

**말하는 것 자체가 버겁다.** 정리하러 왔는데 상황을 처음부터 설명하고 논리적으로 정리해서 말해야 한다.

**대화할수록 생각의 경로를 잃는다.** 어디서 시작했는지, 왜 지금 이야기로 넘어왔는지, 지금 실제로 뭘 묻고 있는지가 흐려진다. 대화 로그는 남지만 **생각이 어떻게 이동했는지는 남지 않는다.**

### 내부 문제 정의
> 답을 찾지 못하는 문제가 아니라, **생각이 진행되면서 내 질문의 중심을 잃어버리는 문제.**

## 2. 시장과 경쟁

**사람이 AI에게 개인적 고민을 말하는 행동은 이미 존재한다.** 새 행동을 만드는 게 아니라 이미 일어나는 행동에서 **휘발되는 부분을 잡는다.** 인접 시장에 유료 수요도 있다(Rosebud 월 $12.99, Mindsera 월 $14.99, Day One Gold 연 $74.99).

| 영역 | 대표 | 하는 일 | Nook과 다른 점 |
|---|---|---|---|
| 범용 AI | ChatGPT | 질문·조언·개인적 대화 | 대화가 기본 객체. Nook은 **질문의 이동 경로**가 기본 객체 |
| AI 저널 | Rosebud, Mindsera, Reflect, Day One | 기록 → 분석 → 통찰 | 사람을 분석. Nook은 **경로를 남김** |
| AI 마인드맵 | Xmind AI, Mapify | 아이디어를 확장·구조화 | 더 펼치는 게 강점. Nook은 **수렴** |
| 멘탈웰니스 | Wysa | 정서 지원, CBT, 임상 근거 | 치료 목적. Nook은 **비임상 생각 정리** |

**주의**
- "AI가 질문해준다"는 차별점이 아니다. Rosebud의 Dig Deeper가 이미 한다. 차이는 **질문의 목적**이다.
- "대화를 시각화한다"도 차별점이 아니다. 차이는 **방향**이다.
- 멘탈헬스와는 의도적으로 거리를 둔다. 붙는 순간 임상 근거·위기 대응·전문가 검증이라는 다른 경기장이 열린다.

### 가장 강한 대비
> **마인드맵은 생각을 펼친다. Nook은 생각의 중심을 찾는다.**

## 3. 검증할 단 하나의 가설

> **사용자는 AI가 답을 주지 않아도, 자신의 질문이 더 선명해지고 그 변화가 눈에 보인다면 충분한 효용을 느끼는가?**

YES면 회고·Question Book·연결·공개로 확장한다. NO면 무엇을 붙여도 코어가 없다.

**사업으로서의 다음 성공은 다르다.** "다음에 또 머릿속이 복잡해졌을 때 ChatGPT 대신 Nook을 다시 열었는가."

## 4. 세션 흐름

| # | 단계 | 내용 |
|---|---|---|
| 1 | Raw Thought | 정리되지 않은 생각 그대로 입력. 예시 칩으로도 시작 |
| 2 | Start Reframe | AI가 시작 질문 제안 → 사용자 확정 → **Node 0** |
| 3 | Reflection | 한 번에 하나씩 되물음 |
| 4 | Judge | 무슨 일이 일어났는지 판정 |
| 5 | Shift Proposal | 중심이 바뀌었을 때만 새 질문 + 근거 제안 |
| 6 | User Confirm | 맞음 / 수정 → 확정된 것만 지도에 저장 |
| 7 | Thought Map | 중심 경로, 한 구간 최대 4노드 |
| 8 | Closure | 종료 화면 + 남겨둔 질문 + 저장 권유 |

### 첫 화면

```
    머릿속에 걸리는 게 있나요?
    정리하지 말고 생각나는 대로 적어주세요

    [                        ]

    이직하고 싶은데 이유를 모르겠어
    계속 만나는 게 맞는지 모르겠어
    사고 싶은데 계속 망설여져
    그냥 머릿속이 복잡해
    ───────────────────────────
    지나온 생각            최근 2~3개
    9월 9일
    이직할까? → 지금 회사에서 원하는 성장이 가능한가?
                              [전체 보기]
    ───────────────────────────
    남겨둔 질문 3개        [열어보기]
```

**예시 칩은 데모 모드가 아니다.** 누르면 그 문장이 실제 Raw Thought가 되어 일반 입력과 같은 흐름을 탄다. 심사용 체험과 실제 서비스를 따로 만들지 않는다.

카테고리를 분산한다. 관계 예시만 크게 두면 연애상담 앱으로 인식된다. **칩 문장은 실제로 Shift가 잘 일어나는지 사전 검증한다.**

**서랍을 첫 화면 주인공으로 만들지 않는다.** 그러면 첫인상이 생각 정리 도구가 아니라 기록장이 된다. 신규 사용자는 입력창만 보이고, 쓸수록 아래가 채워진다.

## 5. 대화 엔진

### 5.1 실행 순서

```
0. Safety Gate           ← Moderation + 별도 Safety Classifier
1. Explicit User Control  ← 코드
2. Structural Check       ← 코드, 숫자만 셈
3. Turn Judge             ← LLM (Prompt B)
4. Reframe / Reflection   ← LLM (Prompt C 또는 D)
5. 사용자 선택
```

**0~2는 결정론적, 3~4만 LLM.** LLM이 판단할 영역을 최소화한다.

**Safety는 Judge 안에 넣지 않는다.** Safety Gate가 대화 엔진 앞에 있다는 원칙이 깨지고, Judge 역할이 다시 넓어진다.

**Structural Check를 Judge에서 뺀 이유:** LLM에게 "노드가 4개인지 세어봐"를 시킬 이유가 없다. 코드가 먼저 확인하고 걸리면 Judge를 호출하지 않는다.

**Explicit User Control이 코드인 이유:** "그만할래"에 Judge를 태우면 못 알아들을 위험만 생긴다.

### 5.2 Shift 판정

**핵심 기준**
> 새로운 이야기가 나왔는가가 아니라, **기존 질문에 답해도 핵심 고민이 더 이상 해결되지 않는 상태인가.**

**Shift는 "처음 질문이 가짜였다"가 아니다.** 대화를 진행하면서 **사용자가 지금 풀고 싶은 중심 질문이 달라진 것**이다. 처음 질문이 완전히 정상이어도 이동할 수 있다. "숨겨진 진짜 고민"으로 설명하면 제품이 심리 발굴 쪽으로 기운다.

**실전 체크**
- 새 질문에 답한 뒤 **원래 질문으로 돌아가야 하는가** → 하위 질문 / Branch
- 새 질문 때문에 **원래 질문 자체를 다르게 보게 되는가** → Shift 후보
- 그 이동을 **사용자가 실제 발화에서 반복·강조했는가** → YES여야 Main Path

**내부 4문**
```
Q1. 기존 질문의 세부조건·증거·정보를 확인하는 중인가?     YES → NOT SHIFT
Q2. 기존 질문에 답해도 새 고민이 남아 있는가?            NO  → NOT SHIFT
Q3. 질문의 대상·기준·레벨 중 하나 이상이 달라졌는가?      NO  → NOT SHIFT
Q4. AI가 끌고 간 게 아니라 사용자 발화에서 반복·강조됐나?  NO  → 보류
                                                     YES → SHIFT 후보
```

**Q4가 게이트다.** Q1~Q3는 문장만으로 판정 가능하지만 Q4는 맥락이 필요하다. AI 질문에 사용자가 "그럴 수도 있겠네요" 한 정도는 증거가 아니다.

**판정 단위는 최근 3~4턴.** 엔진은 `현재 문장 판정기`가 아니라 **`최근 생각 흐름 판정기`**다.

### 5.3 참조 예시

**SHIFT**
| 시작 | 이동 후 |
|---|---|
| 이직할까? | 나는 회사를 떠나고 싶은 걸까, 성장하고 싶은 걸까? |
| 이 관계를 계속할까? | 나는 이 사람이 변하기를 기다리고 있는 걸까? |
| 노트북을 살까? | 필요한 건 성능일까, 좋은 장비를 갖는 만족감일까? |
| 친구에게 서운하다고 말할까? | 원하는 건 사과일까, 중요하게 여겨진다는 확인일까? |
| 대학원을 갈까? | 공부를 더 하고 싶은 걸까, 진로를 미루고 싶은 걸까? |
| 독립할까? | 원하는 게 공간일까, 내 삶을 내가 결정한다는 느낌일까? |

**NOT SHIFT**
| 시작 | 나온 질문 |
|---|---|
| 이직할까? | 연봉이 얼마 이상이면 옮길까? / 통근시간은? |
| 노트북을 살까? | RAM 16GB면 충분할까? |
| 이 관계를 계속할까? | 지난달에도 같은 일이 있었나? |
| 독립할까? | 월세 80만원을 감당할 수 있을까? |

> 질문이 더 구체적이 됐다고 새 노드를 만들면 안 된다.

**AMBIGUOUS** — 문장만으로는 판정 불가, 최근 흐름을 봐야 함
- 이직할까? → 지금 회사에서 성장할 수 있을까?
- 계속 만날까? → 내가 받은 상처를 아직 못 넘긴 걸까?
- 노트북을 살까? → 나는 왜 비싼 물건 살 때 불안하지?
- 퇴사할까? → 일을 쉬고 싶은 걸까?
- 헤어질까? → 내가 외로운 게 두려운 걸까?

**"밖 → 안" 이동은 판정 기준이 아니다.** Shift에서 자주 관찰되지만, 기준으로 쓰면 모든 고민을 내면 탐색으로 끌고 간다.

### 5.4 Confidence 정책

| | 동작 |
|---|---|
| HIGH | Shift 제안 (근거 문장 포함) |
| MEDIUM | 노드 제안 없이 **방향만 확인** |
| LOW | NOT SHIFT, 화면에 표시 없음 |

MEDIUM 문구:
> 지금 이야기가 처음 질문에서 조금 다른 쪽으로 가는 것 같기도 해요.
> **[여전히 처음 질문이 중심이에요] [이쪽이 더 궁금해졌어요]**

후자를 고르면 **사용자 본인이 중심 이동을 선언한 증거**가 되어 다음 턴 confidence가 오른다. 이 응답은 `Check Event`로 저장한다.

**보수 정책**
> False Negative는 허용하고 False Positive Shift를 강하게 줄인다.

**오류 치명도 순서**
1. NOT SHIFT를 SHIFT로 판정 ← 가장 큰 오류
2. CHECK여야 하는데 SHIFT
3. 실제 SHIFT를 늦게 잡거나 놓침

### 5.5 Reframe

요약이 아니라 재정의다.

| | 예 |
|---|---|
| 요약 (X) | 상대의 변화에 대해 이야기했어요 |
| 재정의 (O) | 나는 상대가 변하기를 기다리고 있는 걸까? |

**허용 경계**
> **사용자가 여러 번 말한 것을 하나로 묶는 것은 허용.**
> **사용자가 말하지 않은 원인·성향·심리적 해석을 추가하는 것은 금지.**

- "지금은 잘해준다" + "앞으로 달라질 것 같다" + "기다려보고 싶다" → "나는 상대가 변하기를 기다리고 있는 걸까?" **허용**
- "내가 너무 예민한 걸까?" → "나는 내 감정을 신뢰하지 못하는 걸까?" **금지**

이 경계가 없으면 "심리 원인 발굴 금지" 원칙이 Reframe 자체를 죽인다.

**근거 제시 의무.** 새 노드를 제안할 때 왜 그렇게 봤는지를 한 줄로 함께 낸다.

### 5.6 이 규칙은 모든 문구에 적용된다

Node 생성뿐 아니라 Closure, Clarification, Shift 근거, 종료 화면, 안내 문구, Safety 문구까지 전부.

> **서비스는 관찰된 것 이상을 말하지 않는다.**

- "지금 질문이 처음보다 달라졌어요" → 화면에 근거가 있으므로 **허용**
- "여기서 멈추면 나중에 더 잘 보일 거예요" → 보장할 수 없는 효과, **금지**
- "이건 고민할 일이 아니에요" → 사용자의 고민 가치를 평가, **금지**
- "드시고 싶으면 드세요" → 답을 대신 내림, **금지**

### 5.7 Branch

Shift가 아닌데 새 질문이 나왔으면 전부 Branch → Question Pile.

**조용히 보관한다.** 세션 종료 시 한꺼번에 보여준다.

**Branch 저장과 다음 대화 액션은 별개다.** Branch를 저장한 턴에도 대화는 계속된다.

**Branch → Shift 승격.** Pile은 잠재적 중심 질문 후보 저장소다.

## 6. 단순 질문 처리 (CLEAR_AS_IS)

Prompt A는 모든 입력을 Reframe하지 않는다. 출력이 두 가지다.

| | 의미 |
|---|---|
| `REFRAME_NEEDED` | 현재 질문이 무엇인지 아직 흐림 |
| `CLEAR_AS_IS` | 이미 질문이 충분히 분명함 |

**CLEAR_AS_IS 예:** "오늘 치킨 먹을까?" / "우산 가져갈까?" / "지금 커피 마실까?"

이 경우 억지로 이동시키지 않는다. 억지 Reframe은 우리가 금지한 거의 모든 걸 위반한다 — 사용자가 안 한 말을 만들고, 심리 원인을 발굴하고, Depth Guard를 넘는다.

```
지금 질문은 이미 분명해 보여요.
`오늘 치킨을 먹을까?`

[여기까지 정리하기]  [조금 더 생각해보기]
```

**단, 표면의 가벼움으로 판단하지 않는다.** 판단 기준은 **사용자 발화 자체에 아직 정리되지 않은 갈등이 있는가**다.

- "오늘 치킨 먹을까?" → CLEAR_AS_IS
- "요즘 자꾸 시켜 먹는데 이래도 되나" → REFRAME_NEEDED
- "치킨 먹을까 말까 30분째 고민 중" → REFRAME_NEEDED

**가벼운 대화 상대를 원하는 사용자는 Nook의 타깃이 아니다.** 그건 감정 케어 앱이 더 잘한다. Nook이 줄 수 있는 건 **빠르게 돌려보내는 것**이고, 그것도 제품의 일부다.

---

## 7. Depth Guard

자기이해가 결과로 생기는 건 괜찮다. 자기분석을 목적으로 대화를 끌고 가지 않는다.

**허용 범위:** 행동/선택 → 원하는 것 → 우선순위 → 현재의 기대·전제

**AI가 먼저 열지 않는 영역:** 애착유형, 트라우마, 어린 시절, 결핍, 무의식, 성격 진단, "나는 왜 이런 사람인가"

> **자기이해를 만들기 위해 깊게 파지 않는다. 생각을 선명하게 하다 보니 자기이해가 생길 수는 있다.**

이것이 생각 정리 도구와 상담 AI의 경계다.

## 8. Safety Flow

되묻는 것이 메커니즘인 서비스라 위험이 구조적으로 있다. **대화 엔진과 완전히 분리된 별도 게이트**로 둔다.

### 8.1 감지 — 2단계

```
사용자 발화
  ↓
1차 Moderation API (omni-moderation-latest, 무료)
  ↓
2차 Safety Classifier (Judge와 완전히 별도)
  ↓
NONE → Turn Judge
AMBIGUOUS / HIGH_RISK → Safety Flow
```

**Moderation은 신호, 2차 분류기가 문맥을 판단한다.** Moderation은 유해 콘텐츠 분류기지 "이 사람이 지금 힘들다"를 잡는 도구가 아니다. 그리고 한 번이라도 걸리면 무조건 중단하면 한국어 관용 표현("죽겠다 진짜")에서 오탐이 심해진다.

**2차 분류기 출력은 3단계.** `NONE / AMBIGUOUS / HIGH_RISK`. true/false로 두면 관용 표현과 실제 신호를 같은 통로로 처리하게 된다.

**여기서만 오탐을 허용하는 방향으로 간다.** 놓치는 게 더 나쁘기 때문에, 판정 정책이 나머지와 반대다.

### 8.2 걸리면 멈추는 것

되묻기 중단 · Shift 판정 중단 · 노드 생성 중단 · 지도 갱신 중단.

**서비스의 메커니즘 자체를 끈다.** 질문을 던지는 게 이 제품의 전부인데, 여기서는 그게 위험할 수 있다.

### 8.3 문구

**절대 하지 않는 것**
- 진단 — "우울하신 것 같아요", "많이 힘드신 상태네요"
- 되묻기 — "무슨 일이 있으셨어요?"
- 상태 확인 시도 — 전문가가 할 일이다
- 조언
- 평가 — "그게 나을 것 같아요"도 평가다

**기본형**
```
지금은 질문을 더 이어가지 않을게요.
바로 도움을 받을 수 있는 연락처를 안내할게요.
```

짧을수록 좋다. 길면 그것도 설득이 된다.

### 8.4 연락처 — 상황별로만

**전화번호를 고정 리스트로 모두 노출하지 않는다.** 1366은 폭력 피해 상황용, 1388은 청소년 대상이라 일반 위험 신호에 함께 띄우면 정보만 많아진다.

| 상황 | 안내 |
|---|---|
| 자살·자해 신호 | **자살예방 상담전화 109** (24시간) / 급한 상황이면 **119** |
| 청소년 맥락 | **청소년 상담전화 1388** (24시간) |
| 폭력 피해 맥락 | **여성긴급전화 1366** (24시간) |
| 일반 정신건강 | **정신건강 상담전화 1577-0199** |

> 2024년 1월 1일부터 자살예방 상담전화는 **109**로 통합되었다. 기존 1393은 사용하지 않는다.

### 8.5 이후 흐름

**갇히면 안 된다.** 오탐이 실제로 자주 난다. 그런데 "계속하기"를 두면 우회로가 된다.

**[새 생각 시작하기]** 버튼 하나. 현재 세션은 닫고 새 세션을 연다. 우회로도 아니고, 오탐이어도 사용자가 막히지 않는다. 같은 위험 발화를 다시 입력하면 게이트가 다시 걸린다.

"다른 이야기로"라고 쓰지 않는다. 방금 한 이야기가 부적절했다는 느낌을 준다.

**강제로 창을 닫지 않는다.** 사용자가 나가는 건 자유지만, 서비스가 문을 닫아버리는 경험은 만들지 않는다.

### 8.6 저장 처리

**Safety 화면에서는 아무것도 묻지 않는다.** 위험 안내 직후에 저장 여부를 묻게 하면 Safety 화면이 갑자기 제품 결정 화면이 된다.

| | 처리 |
|---|---|
| 세션 상태 | `SAFETY_STOPPED` |
| 서랍 노출 | 없음 (완료 세션이 아님) |
| Pile 노출 | 없음 |
| 데이터 | **삭제하지 않고 숨김** |
| 위험 신호 발화 원문 | **저장하지 않음** (Judge Log 포함) |

**Pile로 보내지 않는 이유:** 남겨둔 질문에는 "여기서 시작하기"가 붙는다. 힘들었던 순간에 나온 질문이 **다시 시작하라고 권하는 형태로** 남는다. 방금 멈추기로 한 걸 며칠 뒤에 다시 열라고 하는 셈이다. 그리고 더미는 사용자가 선택해 치운 곳인데, Safety는 서비스가 멈춘 것이라 성격이 다르다.

**삭제하지 않는 이유:** Safety는 오탐 허용 방향으로 설계됐다. 오탐 비율이 높은 게이트가 사용자 기록을 지우는 권한까지 갖는 건 과하다. 20분 대화하고 노드 세 개를 만든 세션이 마지막 한마디로 통째로 사라지면 안 된다. 복구 기능은 나중에 검토한다.

**저장하는 것:** `session_id`, `SAFETY_STOPPED`, `safety_category`, `trigger_source`(MODERATION / CLASSIFIER), `created_at`. 원문은 남기지 않는다.

### 8.7 발표에서
> Nook은 질문을 던지는 게 작동 원리라서, 질문을 멈춰야 하는 순간을 판정 구조 맨 앞에 뒀습니다.

## 9. Closure — 세 종류

### A. Soft Closure
AI가 "지금 질문이 충분히 선명해졌다"고 판단. 종료를 강제하지 않는다.

> 처음에는 **"이직할까?"** 에서 시작했고, 지금은 **"성장할 환경을 찾는 걸까?"** 까지 왔어요.
> **[여기까지 정리하기] [이 질문 조금 더 보기]**

버튼 이름은 "그만하기/계속하기"가 아니라 **"정리하기/조금 더 보기"**. 둘 다 사용자가 뭔가를 하는 선택이지, 하나가 거절이 아니다.

**좋은 지점에서의 종료도 Close다.** "아 그러네", "내가 뭘 걸려 했는지 알겠다" 같은 반응이 나오면 거기가 끝이다.

### B. Structural Transition
노드·턴·Branch 상한 도달. **"그만하라"가 아니라 사고 단위를 나누는 것이다.**

> 여기까지 하나의 생각 흐름이 만들어졌어요. 이 질문에서 더 이어갈 수도 있어요.
> **[이 질문에서 이어가기] [여기까지 정리하기]**

**대화만 계속하고 지도를 멈추면 안 된다.** 그러면 대화와 기록이 다시 분리되어 원래 문제를 재생산한다.

### C. Safety Stop
8장 참조. **여기서만 "계속 보기"가 없다.**

### Intentional Closure 정의
> **더 이상 질문할 수 없는 순간이 아니라, 더 질문할 수 있어도 지금 정리할 가치가 있는 순간을 알아차리는 것.**

## 10. 구간과 Anchor

사용자에게 "Map 1 / Map 2"라고 보여주지 않는다. **하나의 생각 흐름 안의 여러 구간**이다.

새 구간은 독립적인 Node 0을 만들지 않는다.
> **이전 구간의 마지막 확정 Node를 Anchor로 이어받는다.**

데이터에서는 노드를 복제하지 않고 참조한다. 구간 2를 그릴 때 첫 노드를 Anchor에서 읽어와 표시하되, **구간 2의 소유 노드로 카운트하지 않는다.**

> **지도 구간은 여러 개여도 Thought Path는 하나다.**

## 11. 시각화

### 화면 요소 다섯 개

| 요소 | 의미 | 생성 기준 |
|---|---|---|
| **Main Node** | 질문의 **진전** | HIGH Shift + 사용자 승인 |
| **Clarification** | 같은 질문 안에서의 **진행** | 의미 있는 범위 축소 |
| **Shift Evidence** | 왜 이동했는가 | 노드 사이 연결선에 한 번 |
| **Pile indicator** | 따라가지 않은 질문 | 개수만 |
| **Current Question** | 지금 묻고 있는 것 | 항상 |

```
      지금 묻고 있는 것
   나는 성장할 환경을 찾는 걸까?
   ─────────────────────────

        ● 이직할까?
        │
        │  회사 자체가 싫은 건 아님
        │  반복 업무가 계속 걸림
        │
        │  남겨둔 질문 2
        │
        ↓  회사보다 성장 얘기가 중심이 됨
        │
        ● 나는 성장할 환경을 찾는 걸까?
        │
        ◉  ← 지금 여기
```

### Clarification

**Reframe 규칙 동일 적용.** 범위를 좁혀 표현하는 것은 가능, 새 의미·원인·성향 추가는 금지.
- 허용: `회사 자체가 싫은 것은 아님`
- 금지: `결국 성장 욕구가 충족되지 않는 것이 핵심`

**한 Node 구간에 화면 표시 최대 2~3개.** **HIGH confidence만 반영.**

**Clarification은 수정될 수 있다.** 나중에 사용자 말이 바뀌면 교체하거나 제거한다.

| | 성격 | 저장 |
|---|---|---|
| Main Node | 승인된 사고의 역사 | append only |
| Clarification | 현재까지 확인된 보조 정보 | mutable |

### 절대 넣지 않는 것

**턴마다 찍히는 점.** "모르겠어"를 네 번 말해도 점 네 개가 생기면 화면이 거짓말을 한다.

**진행률 표현.** `1/4`, `50%`, 완성도 게이지. **4는 시스템 상한이지 사용자 목표가 아니다.**

**"생각 정리 중" 같은 가짜 진행 표시.** 아무 일도 없었으면 화면이 그대로 있는 게 맞다.

**Branch 내용의 실시간 노출.** 안 보기로 한 생각을 화면에 보여주면 사용자가 다시 읽고 생각한다.

### Shift 0 세션

보수적 Judge 때문에 자주 나온다. 정상 결과다.

> 처음 질문은 그대로예요. **이직할까?**
> 대신 이야기하면서 몇 가지가 분명해졌어요.
> · 회사 자체가 싫은 것은 아니었어요
> · 사람 관계가 가장 큰 이유도 아니었어요
> · 반복되는 업무가 계속 걸렸어요
>
> **질문은 바뀌지 않았지만, 처음보다 범위가 좁아졌어요.**

### 시각화 원칙
> **노드는 질문의 이동을 보여준다.**
> **Clarification은 같은 질문 안에서 실제로 선명해진 것만 보여준다.**
> **대화량이나 시간을 진행처럼 표현하지 않는다.**
> **따라가지 않은 질문은 존재만 알리고 시야에서는 치운다.**
> **지도는 진행률이 아니라 사고의 흔적이다.**
> **아무것도 선명해지지 않은 순간에는, 아무것도 추가하지 않는 것이 정확한 시각화다.**

## 12. 지나온 생각

### 목록

**Shift가 있었던 세션**
```
9월 9일
이직할까? → 지금 회사에서 원하는 성장이 가능한가?
```
이 두 줄이 제품 그 자체다. 목록을 넘길 때마다 **질문이 이동했다는 사실**이 반복해서 보인다.

**Shift 0 세션** — `이직할까? → 이직할까?`로 표시하지 않는다. 질문 + 대표 Clarification.
```
9월 9일
이직할까?
반복 업무가 계속 걸린다는 점이 분명해짐
```
새 요약문을 만들지 않고 저장된 Clarification 중 하나를 참조한다.

### 상세
그날의 Thought Path, Main Nodes, Shift Evidence, Clarification, 남겨둔 질문.

**대화 전문은 기본 표시하지 않는다.** 남기려는 것은 대화 기록이 아니라 경로다. 데이터가 존재하는 것과 UI에서 보여주는 것은 다른 문제다.

### 성장감
시스템이 "성장했어요"라고 말하지 않는다. 과거와 현재의 질문을 나란히 놓고 사용자가 스스로 느끼게 한다.

> **감정을 주입하지 않는다. 감정을 느낄 재료를 남긴다.**
> **쌓인 양을 보여주지 말고 쌓인 내용 자체를 보여준다.**

금지: 이번 달 질문 12개, 지난달보다 +3개, 연속 7일, 질문 개수 그래프.

**반복 질문 표시는 MVP에서 제외한다.** "이 질문은 세 번 나왔어요"를 하려면 "같은 질문"을 판정하는 유사도 로직이 또 필요하다. 새 문제를 하나 더 만들지 않는다. → Question Graph 단계로 이동.

## 13. 남겨둔 질문

UI 표기는 **남겨둔 질문**. 내부적으로 Pile/더미로 부른다.

**"미해결 질문"이라 부르지 않는다.** 숙제가 아니라 오늘 다루지 않기로 선택한 질문이다.

### 동작 두 개
- **여기서 시작하기** — 그 질문이 새 세션의 Raw Thought가 된다. 원본 세션과의 연결을 저장해 "9월 9일에 남겨둔 질문에서 이어졌어요"를 보여줄 수 있다.
- **삭제** — 확인 후 **영구 삭제**

별도의 가리기·보관·숨김 단계를 만들지 않는다. Pile 자체가 이미 가려둔 장소다.

### 삭제 정책
**영구 삭제로 통일한다.** 개인 고민을 다루는 서비스에서 "삭제를 눌렀는데 서버에 남아 있는" 구조는 설명할 게 늘고 신뢰에 해롭다.

```
이 질문을 삭제할까요?
삭제하면 다시 볼 수 없어요.
[취소] [삭제]
```

### 두 문구의 대상을 분리한다
- Pile 목록 상단: **"여기 남긴 질문은 사라지지 않아요"** → 남겨둔 것에 대한 약속
- 삭제 확인: **"삭제하면 다시 볼 수 없어요"** → 지우는 행동에 대한 경고

대상이 다르므로 충돌하지 않는다. 아무것도 안 하면 안 사라지고, 명시적으로 지우면 사라진다.

**단, "사라지지 않아요"는 로그인한 사용자에게만 띄운다.** 익명 상태에서는 재접근이 보장되지 않는다. 서비스가 보장할 수 있는 말만 한다.

## 14. 인증

**MVP는 구글 / 카카오 소셜 로그인만.** 이메일+비밀번호는 후순위. 구조는 열어둔다.

**로그인 시점은 첫 화면이 아니다.**
```
익명 사용자로 세션 진행 → 지도 완성 → 종료 화면
                    "이 생각을 남겨둘까요?"
                    [저장하기]  [그냥 나가기]
                         ↓
                   구글 / 카카오 연결
                         ↓
              같은 사용자 ID 그대로 유지
```

### Supabase Identity Linking을 사용한다

익명 사용자에게도 처음부터 user ID가 있고, 나중에 OAuth identity를 **연결**하는 구조다. 프로젝트에서 manual linking을 활성화해야 한다.

**앱에서 이메일을 비교해 계정을 임의 병합하지 않는다.** Supabase가 확인된 동일 이메일의 identity를 자동 연결하는 기능을 제공한다. 그리고 **카카오는 이메일이 선택값**이라 이메일 기준 병합은 애초에 성립하지 않을 수 있다.

이 방식이면 "익명 세션을 계정으로 이전"하는 별도 처리도 필요 없다. 같은 사용자 ID가 유지되기 때문이다.

**저장 안 하고 나가는 것도 정상 경로다.** 강제하지 않고 팝업을 반복하지 않는다.

## 15. 기술 구조

**별도 백엔드 서버를 만들지 않는다.**

```
프론트 + API   Next.js (한 프로젝트, app/api/)
배포          Vercel
DB + 인증      Supabase (PostgreSQL + Auth)
AI            OpenAI
안전 1차       OpenAI Moderation (무료)
코드          GitHub
```

**분리하지 않는 이유:** 서버를 나누면 일이 늘어나는 게 아니라 **실패 지점이 늘어난다.** 배포 두 번, 환경변수 두 벌, 도메인 두 개, CORS, 토큰 전달. 이런 건 막혔을 때 원인을 찾기 어렵고, 마감이 11일이다. 같은 구조적 분리는 `app/api/` 안에서도 똑같이 할 수 있고, 나중에 분리하고 싶으면 그 폴더를 옮기면 된다.

**모델은 두 단계로 쓴다.**

| 작업 | 모델 |
|---|---|
| Turn Judge, Reflection, Branch/Clarification 추출 | 저가 모델 |
| Node 0 Reframe, Shift Reframe | 고성능 모델 |

비싼 모델이 필요한 순간은 **사용자의 지도에 영구히 남을 문장을 만드는 때**뿐이다. Judge는 매 턴 도는 구조화된 판정이라 저가 모델부터 시작하고, 테스트에서 False Positive가 많으면 그때 올린다.

**비용 안전장치**
- API 키는 절대 프론트에 두지 않는다. 서버 함수에서만 호출, 환경변수로 관리
- 선불 크레딧 소액 충전 + **자동 충전 OFF**
- IP당 사용량 제한 — 링크가 퍼지면 API 비용이 폭탄이 된다

**넣지 않는 것:** Redis, 벡터 DB, 임베딩, 별도 분석 도구, ORM, Docker, 별도 백엔드 저장소.

**비용 예상:** Supabase·Vercel·로그인·Moderation 모두 무료 범위. 실제 지출은 AI 호출뿐이고 대회 기간 만 원 안쪽.

## 16. 데이터 구조

### 핵심 원칙
> **대화 자체보다 질문의 이동을 중심 데이터로 저장한다.**
> **완료된 세션이 곧 '지나온 생각'이다. 같은 내용을 두 번 저장하지 않는다.**
> **Node는 지나온 사고의 역사, Clarification은 현재 이해라 수정될 수 있다.**
> **구간은 여러 개여도 하나의 Thought Path로 연결한다.**
> **AI 판정 결과와 사용자에게 보여줄 기록은 분리한다.**

### 엔티티

| | 역할 |
|---|---|
| **User** | 사용자 (익명 → identity linking) |
| **Thought Session** | 한 번의 생각 흐름 |
| **Segment** | 긴 세션의 구간 (Anchor로 이전 구간 마지막 노드 참조) |
| **Message** | 실제 대화 |
| **Question Node** | 중심 질문 (START / SHIFT) |
| **Shift Edge** | 질문이 이동한 이유 + 근거 발화 |
| **Clarification** | 같은 질문 안에서 선명해진 것 (유효 여부 포함) |
| **Check Event** | MEDIUM 확인에 대한 사용자 응답 |
| **Pile Item** | 남겨둔 질문 |
| **Session Feedback** | 종료 설문 |
| **Judge Log** | 개발용, 사용자 기록과 분리 |

### 카운터 위치 — 중요

```
SESSION
  check_count

SEGMENT
  node_count
  turn_count
  branch_count
```

**Session에 turn_count를 두면 안 된다.** 구간 1이 20턴이라 구간 2를 열었는데 Session 카운터가 20이면 **새 구간을 시작하자마자 또 상한에 걸린다.** 구간을 나눈 이유가 계속하게 해주려는 건데 정반대로 작동한다.

CHECK만 세션 단위인 이유는 "취조받는 느낌"을 막는 게 세션 전체 경험의 문제이기 때문이다.

### Check Event
```
id
session_id
current_node_id
candidate_direction
user_choice        // CURRENT_QUESTION | NEW_DIRECTION
evidence_turns
created_at
```

Node가 아니다. **사용자가 어느 방향을 중심이라고 선언했는지를 남기는 판정 보조 데이터**다. 저장되지 않으면 CHECK 기능 자체가 무의미하다.

### 그 밖에 반드시 포함할 것
- **Question Node**: AI 제안 문장과 사용자 최종 문장을 **둘 다** 저장 — 승인률과 수정률이 핵심 지표
- **Pile Item 상태**: `ACTIVE` / `RESUMED` (삭제는 실제 삭제)
- **Session 상태**: `ACTIVE` / `COMPLETED` / `SAFETY_STOPPED`

### Judge 출력 스키마

Branch는 액션이 아니라 side effect이므로 단일 라벨로 반환하지 않는다.

```json
{
  "action": "CLOSE | SHIFT | CHECK | REFLECT",
  "branches": [
    { "text": "새로 발견된 갈래", "evidence_turns": ["U2"] }
  ],
  "clarification": {
    "text": "반복 업무가 계속 걸림",
    "evidence_turns": ["U3"],
    "confidence": "HIGH"
  },
  "shift_confidence": "HIGH | MEDIUM | LOW",
  "evidence_turns": ["U1", "U3"]
}
```

`clarification`은 없으면 `null`. **evidence_turns는 사용자 발화 번호만** 사용한다. AI가 자기가 만든 질문을 다시 근거로 쓰는 순환을 막는다.

## 17. 프롬프트 네 개

### Prompt A — Start Reframe
Raw Thought → 시작 질문. 출력은 `REFRAME_NEEDED` 또는 `CLEAR_AS_IS`(6장 참조).
- 사용자 발화 재료만 사용
- 없는 원인·성향 추가 금지
- 확신이 낮으면 원문에 가깝게
- 사용자 승인 전 확정하지 않음

### Prompt B — Turn Judge
입력: 현재 Main Question, 최근 3~4턴, Main Path, 현재 Branch/Pile, 최근 Check Event
출력: action, branches, clarification, confidence, evidence

> **Judge는 문장을 만들지 않는다. 판정만 한다.**

판정과 생성을 같이 시키면 모델이 멋진 질문을 만들고 싶어서 Shift를 과대판정한다. 규칙으로 못 막고 구조로 막아야 한다. **근거 문장도 Judge가 쓰지 않는다.**

**호출 시점:** 대화 응답보다 판정을 먼저. Judge → 결과에 맞는 응답 생성.

### Prompt C — Shift Reframe
Judge가 SHIFT를 반환했을 때만 호출. 새 중심 질문 + 근거 한 줄.

### Prompt D — Reflection Generator
Judge가 REFLECT를 반환했을 때만 호출. 사용자에게 던질 실제 질문 하나를 생성.

**이건 추가 기능이 아니라 빠진 엔진 부품이다.** Judge가 REFLECT라고 판정해도 실제 질문을 만드는 주체가 없으면 대화가 멈춘다. Judge에 합치면 과대판정 문제가 되살아난다.

규칙:
- 현재 Main Question을 바꾸지 않는다
- 한 번에 하나만 묻는다
- 사용자가 말하지 않은 심리 원인을 열지 않는다
- 현재 질문의 모호한 부분만 좁힌다

### "조금 달라요"
사용자가 직접 자유 편집한다. AI가 대안을 다시 생성하지 않는다.

## 22. 지표

### 세션 종료 1문항
> 오늘 시작할 때보다 무엇을 고민하는지 선명해졌나요?
> **네 / 비슷해요 / 잘 모르겠어요**

세션 시작 시에는 묻지 않는다. 진입 전 자기 상태 평가 요구는 "정리해서 말하기가 버겁다"는 문제 정의와 충돌한다.

### 개발 중 확인
세션당 Shift 수 · Shift 0 세션 비율 · Shift Proposal 승인률 · "조금 달라요" 비율 · 종료 설문 응답 · 중도 종료율 · CHECK 사용 빈도 · **Safety 발동률과 오탐 체감**

| 조합 | 해석 |
|---|---|
| 노드 0 + "선명해졌다" | 성공. 되물음만으로 효용 발생 |
| 노드 0 + "비슷하다" | 판정이 너무 빡빡함 |
| 노드 여럿 + 수정률 높음 | 과잉해석 |
| 노드 여럿 + 승인률 높음 + "선명해졌다" | 이상적 |

## 23. 제품 원칙

> **답을 대신 내리지 않는다.**
> **안전과 종료를 항상 먼저 판단한다.**
> **새로운 내용이 아니라 주된 질문이 바뀌었는지를 본다.**
> **사용자가 실제로 이동하지 않았다면 AI가 이동을 만들어내지 않는다.**
> **애매하면 노드를 만들지 않고 사용자에게 방향만 확인한다.**
> **사용자가 말한 재료는 묶을 수 있지만, 없는 원인과 성향은 만들지 않는다.**
> **이 규칙은 노드뿐 아니라 서비스의 모든 문구에 적용된다.**
> **자기이해는 결과로 생길 수 있지만 자기분석을 목적으로 파고들지 않는다.**
> **더 많이 열지 않는다. 지금 중요한 질문 하나를 선명하게 한다.**
> **AI는 멈춰도 되는 순간을 제안하지만, 멈출지는 사용자가 결정한다.**
> **사용자의 생각을 끊지 않는다. 필요하면 흐름을 새 구간으로 나눈다.**
> **시스템은 사용자가 많이·멀리·깊게 생각했다고 평가하지 않는다.**
> **사용자의 고민이 별거 아니라고 평가하지 않는다.**
> **쌓인 양이 아니라 쌓인 내용을 보여준다.**
> **따라가지 않은 생각은 버리지 않되, 시야에서는 치운다.**
> **지도는 진행률이 아니라 사고의 흔적이다.**

### 품질의 정의
> **좋은 AI는 많은 통찰을 만드는 AI가 아니라, 사용자가 실제로 이동한 생각만 정확히 붙잡고 사용자가 하지 않은 해석은 만들지 않는 AI다.**

## 24. 차별점

| | |
|---|---|
| **Question Reframing** | 흩어진 말을 현재의 중심 질문으로 재정의 |
| **Shift Detection** | 질문 자체가 달라진 순간만 감지 |
| **Intentional Closure** | 더 물을 수 있어도 지금 정리할 가치가 있는지 판단 |
| **Thought Path Accumulation** | 대화방이 아니라 지나온 질문의 경로가 축적 |

> **많이 생성하는 AI가 아니라, 무엇을 남기지 않을지 판단하는 AI.**

### ChatGPT와의 관계
"ChatGPT로는 할 수 없다"고 주장하지 않는다. 기술적으로 가능하고 바로 반박당한다.

> **범용 채팅에서는 사용자가 별도로 요청해야 하는 '현재 질문 고정 · 질문 이동 구조화 · 경로 저장'이, Nook에서는 기본 경험이자 기본 데이터 구조다.**
> 기존 AI에는 대화방이 쌓이고, Nook에는 지나온 질문이 쌓인다.

### 첫 사용에서 이기는 이유
축적은 두 번째부터 작동한다. 첫 세션의 이유는 따로 있다.
- 정리해서 말하지 않아도 시작된다
- 지금 묻는 게 뭔지가 항상 화면에 있다
- 끝났을 때 남는 게 대화가 아니라 경로다

**첫 사용은 이 셋이 이기고, 두 번째부터 쌓인 질문이 지킨다.**

---

## 25. 확장 방향

| 단계 | 제품이 하는 일 | 쌓이는 가치 |
|---|---|---|
| 1. Thought Path | 한 고민을 정리하고 경로 저장 | 오늘 내가 뭘 고민했는지 |
| 2. Question Graph | 여러 세션의 반복 질문 연결 | 어떤 질문을 반복해서 만나는지 |
| 3. Revisit | 과거 질문에서 다시 시작 | 같은 문제를 과거와 지금 어떻게 다르게 보는지 |
| 4. Question Book | 사고 경로를 읽을 수 있는 기록으로 | 내 생각의 아카이브 |

**여기까지만 말한다.** 이후는 아직 모른다. 없는 로드맵을 그리는 것보다 모른다고 말하는 것이 강하다.

### 확장의 근거는 계획이 아니라 구조
엔진에 '고민'이라는 도메인이 없고, **질문과 이동 경로**가 v1 스키마에 이미 있다. 이 데이터는 대화 로그로는 만들 수 없다.

### 소셜은 초기 BM이 아니다
붙인다면 "고민 올리기 → 댓글 조언"이 아니라 **"다른 사람은 이 고민을 어떤 질문을 지나며 생각했는가"**다. **전부 Private가 기본**이고, 공개 전 개인 식별 정보 확인이 필요하다.

## 26. BM

**Freemium + Subscription.** 한국 초기 가설은 월 7,900~12,900원. **"한 달 뒤에도 기록을 다시 열어보는가"가 확인된 뒤에 가격을 테스트한다.**

**무료:** 생각 정리 세션, Thought Path, 지나온 생각, 남겨둔 질문, 기본 재방문. 코어를 막으면 제품 가설 자체를 검증할 수 없다.

**유료:** 쌓인 생각을 더 잘 활용해주는 영역 — 여러 달의 Path 연결, 반복 질문 발견, 과거와 현재 비교, 내보내기.

**AI 크레딧 모델은 쓰지 않는다.** "AI 질문 7회 남음"이 뜨는 순간 사용자가 "이 말까지 해야 하나"를 계산한다. **"정리하지 말고 편하게 말하세요"와 정면으로 충돌한다.**

**회사에 직원 고민 데이터를 파는 방식은 하지 않는다.** 수익 기회가 아니라 금지 항목이다.

장기 B2B는 코칭·교육 쪽. 사용자가 **허용한 Thought Path만** 공유하는 형태.

## 27. 리스크

| | 내용 | 대응 |
|---|---|---|
| **범용 AI 흡수** | ChatGPT의 기억·시각화가 좋아지면 흡수 가능 | moat를 지도 UI로 잡지 않는다. 축적된 Question Graph + 판정 품질 + 신뢰 |
| **과잉 해석** | 엉뚱한 질문을 만들면 AI 오류가 아니라 "나를 이상하게 해석한다"가 된다 | 보수적 Judge. 일반 챗봇보다 오답 비용이 훨씬 크다 |
| **프라이버시** | 매우 민감한 데이터 | 삭제권·저장 여부·공개 기본 OFF·데이터 소유권 |
| **보수 정책과 데모의 충돌** | Shift가 안 생기면 화면에 아무 일도 안 일어난다 | 예시 칩을 사전 검증. Shift 0 세션 종료 화면 설계 |
| **Safety 오탐** | 관용 표현에서 자주 걸린다 | 2단계 분류 + 3단계 출력 + 새 생각 시작하기 |
| **리텐션** | 한 번 쓰고 안 돌아올 수 있다 | 서랍과 남겨둔 질문. 두 번째 방문의 화면이 다르다 |
