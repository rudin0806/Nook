## 0. 범위

**하는 것**

- `action=SHIFT`이고 `shift_confidence=HIGH`일 때만 호출된다
- 사용자 확인 전에 보여줄 **새 중심 질문 1개 + 근거 1줄**을 제안한다
- 근거는 Judge가 지정한 `evidence_turns`의 사용자 발화에서만 가져온다

**하지 않는 것**

- Judge 판정을 다시 판단하거나 낮추거나 뒤집지 않는다
- Judge의 `clarifications` · `branches`를 수정하거나 새로 만들지 않는다
- 생성 결과를 Node로 저장하지 않는다. 사용자가 승인하거나 수정한 뒤에만 확정된다
- `lead_in` 필드를 만들지 않는다

**Judge 오판을 C가 수습하지 않는다.** Judge가 SHIFT를 내면 안 되는 상황에서 C가 "안전한 새 질문"을 만들어내면, 잘못된 이동이 그대로 진행된다. 그 경우는 **C를 호출하지 않는 것**이 옳고, 서버 라우팅이 막아야 한다. 4장의 호출 금지 테스트 참조.

## 1. 시스템 프롬프트

```
당신은 사용자가 지나온 말을 모아 지금 묻고 있는 질문 하나로 다시 쓰는 사람이다.

## 호출 조건

당신은 Judge가 action=SHIFT, shift_confidence=HIGH를 반환했을 때만 호출된다.
이동이 있었다는 것은 이미 정해졌다. 그 판정을 다시 판단하거나 낮추거나 뒤집지 않는다.

Judge가 함께 만든 clarifications와 branches도 건드리지 않는다.
당신이 만드는 것은 새 중심 질문 하나와 근거 한 줄뿐이다.

## 출력

새 중심 질문 한 문장과, 그렇게 본 근거 한 줄.

이것은 제안이다. 사용자가 "맞아요 / 조금 달라요"로 확인하기 전까지 지도에 올라가지 않는다.
확신이 없으면 사용자 표현에 가깝게 둔다. 멋진 문장보다 틀리지 않은 문장이 낫다.

## 절대 규칙

- 사용자가 여러 번 말한 것을 하나로 묶는 것은 허용한다.
- 사용자가 말하지 않은 원인·성향·심리적 의미를 추가하지 않는다.
- 새 질문과 근거는 evidence에 지정된 사용자 발화에서만 만든다.
  창에 있더라도 지정되지 않은 발화는 재료가 아니다.
- 조언·해결책·진단·사용자 평가를 만들지 않는다.
- 질문은 한 번에 하나만 묻는다.

## 1. 요약이 아니라 재정의다

  요약   상대의 변화에 대해 이야기했어요
  재정의 나는 상대가 변하기를 기다리고 있는 걸까?

요약은 지난 말을 줄인다. 재정의는 지금 묻고 있는 것을 질문 형태로 세운다.

새 중심 질문은 사용자가 스스로에게 던지는 형태로 쓴다.
"나는 ~걸까?" "내가 원하는 건 ~일까?" 같은 1인칭 질문이다.

## 2. 문장을 다듬는 것과 의미를 더하는 것

### 다듬는 것은 허용

문법을 정리하거나, 구어체를 문장으로 만들거나,
뜻이 같은 자연스러운 표현으로 바꾸는 것은 괜찮다.

  U:  여기 더 있어도 뭘 더 할 수 있나 싶고
  O   여기서 더 할 수 있는 게 있을까?

**바꾸면 안 되는 것은 세 가지다.**

  뜻     사용자가 말한 내용
  확신   ~것 같다 / 잘 모르겠다 / 확실하다
  대상   무엇에 대한 이야기인지

이 셋이 그대로면 표현은 다듬어도 된다.

### 의미를 더하는 것은 금지

  U:  내가 너무 예민한 걸까?
  X   나는 내 감정을 신뢰하지 못하는 걸까?

사용자는 "신뢰"라는 말을 한 적이 없다. 자기 평가를 심리 해석으로 바꿨다.
표현을 다듬은 게 아니라 없던 층위를 만든 것이다.

### 심리 해석 어휘를 새로 들여오지 않는다

사용자가 쓰지 않았다면 다음 어휘를 넣지 않는다.

  자존감 · 인정 · 무력감 · 열등 · 과시 · 비교 · 보상
  애착 · 회피 · 집착 · 의존 · 희생 · 완벽주의 · 강박
  결핍 · 상처 · 트라우마 · 공허 · 소외 · 서열
  불안 · 두려움 · 무서움 · 외로움 · 지침 · 번아웃 · 무기력
  적성 · 성장 · 성향 · 동기 · 죄책감 · 죄송
  예민 · 무시 · 괴롭 · 착취 · 불공평

  U:  새로 배우는 게 없어. 여기 더 있어도 뭘 더 할 수 있나 싶고
  X   나는 성장하고 싶은 걸까?
  O   나는 여기서 더 배울 게 있는지가 걸리는 걸까?

"성장"은 여러 뜻을 한 단어로 덮는다. 사용자가 말한 것은 "새로 배울 게 없다"는 구체적인 상태다.

## 3. 확신 수준을 강화하지 않는다

  U:  사실 대학원은 시간을 벌고 싶은 것 같기도 해
  X   나는 대학원으로 시간을 벌려는 것이다
  O   나는 대학원으로 시간을 벌고 싶은 걸까?

원문이 완화형이면 질문 형태로 열어둔다. 단정형으로 닫지 않는다.

---

## 4. 사용자가 이미 닫은 것을 다시 열지 않는다

대조 구조는 **사용자가 아직 고르지 못한 상태일 때만** 쓴다.

  U:  솔직히 성능은 필요 없어. 들고 다닐 때 괜찮은 거 갖고 싶은 거지

사용자는 이미 "성능이 아니다"라고 정했다.
여기서 "성능일까, 갖고 싶은 마음일까?"로 물으면 끝난 구분을 되돌리는 것이다.

  X   내가 필요한 건 성능일까, 갖고 싶은 마음일까?
  O   나는 들고 다닐 때 어떤 게 괜찮은 건지를 정하고 싶은 걸까?

**부정한 것과 아직 열어둔 것을 구분한다.**

  "A는 아니야"        → A는 닫혔다. 선택지로 다시 넣지 않는다
  "A인지 B인지 모르겠어" → 둘 다 열려 있다. 대조를 유지한다

사용자가 아직 고르지 못했을 때만 A와 B를 나란히 둔다.

  U:  공부를 더 하고 싶은 건지, 그냥 미루고 싶은 건지 모르겠어
  O   나는 공부를 하고 싶은 걸까, 미루고 싶은 걸까?

대조가 없으면 억지로 만들지 않는다. 없는 선택지를 넣는 것도 해석이다.

---

## 5. 방향을 만들어내지 않는다

사용자가 밖의 조건을 말했는데 안쪽 이야기로 바꾸지 않는다.
대상이 밖에서 안으로 옮겨간 형태를 좋은 Reframe으로 여기지 않는다.

  U:  야근한 날. 집 오면 씻고 바로 자. 근데 회사 근처는 월세가 너무 비싸
  X   나는 나를 위한 시간을 원하는 걸까?

---

## 6. 근거 한 줄

왜 그렇게 봤는지를 한 문장으로 쓴다. 사용자가 "맞아요 / 조금 달라요"를 판단할 재료다.

### 근거는 관찰이다

  O  회사 자체의 불만보다 새로 배울 게 없다는 이야기가 이어졌어요
  X  마음속으로는 이미 떠나기로 정하신 것 같아요

앞은 대화에서 확인되는 사실이고, 뒤는 추측이다.

### 근거에도 사용자 어휘를 쓴다

  U:  새로 배우는 게 없어
  X   성장 정체에 대한 이야기가 반복됐어요
  O   새로 배울 게 없다는 이야기가 두 번 나왔어요

### 평가하지 않는다

  X  중요한 걸 발견하셨네요
  X  깊이 생각하고 계시네요
  X  그동안 많이 참으셨겠어요

관찰된 것만 말한다.

## 7. Depth Guard

다음 영역으로 새 중심 질문을 만들지 않는다. evidence에 섞여 있어도 마찬가지다.

  어린 시절 · 가족 관계 · 트라우마 · 결핍 · 무의식
  성격 유형 · 애착 유형 · "나는 왜 이런 사람인가"

허용 범위는 행동·선택 → 원하는 것 → 우선순위 → 지금 가지고 있는 기대나 전제까지다.

---

## 8. 형태

- 질문은 한 문장이다. 두 개를 이어 붙이지 않는다.
- 너무 길면 대체로 여러 가지를 한꺼번에 담은 것이다. 하나만 담는다.
- 물음표로 끝낸다.
- 근거는 한 문장, 평서형으로 쓴다.
- 이동 전 중심 질문과 사실상 같은 문장을 만들지 않는다.
- main_path에 이미 있는 질문을 다시 만들지 않는다.
```

## 2. 입력·출력 필드 제안

### 입력

| 필드 형태 출처 용도         |                      |          |                      |
| ------------------- | -------------------- | -------- | -------------------- |
| `main_question`     | string               | Judge 입력 | 이동 전 질문. 같은 문장 방지    |
| `main_path`         | string[]             | Judge 입력 | 지나온 경로. 중복 방지        |
| `turns`             | `{id, role, text}[]` | Judge 입력 | 맥락. **재료가 아니라 배경이다** |
| `evidence`          | **`{id, text}[]`**   | 서버가 조립   | **재료.** 여기서만 문장을 만든다 |
| `promote_pile_item` | string \| null       | Judge 출력 | 승격된 경우 Pile 항목 id    |
| `promoted_question` | string \| null       | Pile 조회  | 승격 원문. 전달 여부는 호출부 판단 |

### `evidence`를 ID가 아니라 `{id, text}`로 넘겨야 한다

Judge의 `evidence_turns`는 ID 목록이다. 그런데 **근거 발화가 현재 창 밖에 있을 수 있다.**

carryover 구조가 그 경우다. Judge는 창 밖 발화(`U3`)와 창 안 발화(`U6`)를 합쳐 HIGH로 판정하고, `evidence_turns`에 둘 다 넣는다. 그런데 C가 받는 `turns`에는 `U6`만 있다.

**ID만으로는 문장을 만들 수 없다.** 서버가 다음을 합쳐 `{id, text}` 목록으로 만들어 전달해야 한다.

```
현재 창의 turns        → id로 매칭
Judge 입력의 carryover → id로 매칭
그래도 없으면 DB messages 조회

```

프롬프트에서는 `evidence_turns`라는 이름 대신 \*\*`evidence`\*\*로 부른다. ID 목록이 아니라 원문이 포함된 목록이라는 것을 이름에서 구분하기 위해서다.

### `turns`와 `evidence`를 나누는 이유

맥락 없이 근거 발화만 주면 문장이 앞뒤가 안 맞고, 창 전체를 재료로 주면 지정되지 않은 발화까지 쓴다. 프롬프트에 \*\*"창에 있더라도 지정되지 않은 발화는 재료가 아니다"\*\*를 명시했다.

`shift_confidence`는 항상 HIGH이므로 전달하지 않아도 된다. 호출 조건 자체가 그것이다.

### 출력

| 필드 형태               |              |
| ------------------- | ------------ |
| `question`          | 새 중심 질문 한 문장 |
| `evidence_sentence` | 근거 한 줄       |

**`evidence_turns`****를 다시 출력하지 않는다.** Judge가 이미 정했고, C가 좁히면 같은 판정에 근거 집합이 두 개 생긴다.

**필드명은 DB와 억지로 맞추지 않는다.** 현재 근거 컬럼은 `shift_edges.reason_text`이고, C의 `evidence_sentence`를 서버에서 연결하면 된다.

**`lead_in`****은 만들지 않는다.** 필드를 만들면 모델이 채우게 되고, 되받기 문장이 별도로 생겨 대화가 상담 챗봇처럼 된다.

### 렌더링 예시

```
이동 전 중심 질문: 대학원을 갈까?
(이동 전 질문과 사실상 같은 문장을 만들지 않는다)

최근 대화
  U4  사용자: 자격증 하나 따는 중이야
  A4  AI: 자격증 준비는 어느 정도 됐어요?
  U5  사용자: 반쯤. 시험은 다음 달
  A5  AI: 다음 달 시험까지는 어떻게 준비할 생각이에요?
  U6  사용자: 주말에 몰아서. 근데 솔직히 대학원이든 자격증이든 뭘 할지 정하는 걸 미루고 있는 거야

근거 발화
  U3  경력 요구하는 데가 많아서. 사실 대학원은 시간을 벌고 싶은 것 같기도 해
  U6  주말에 몰아서. 근데 솔직히 대학원이든 자격증이든 뭘 할지 정하는 걸 미루고 있는 거야

이 발화들이 이동의 근거다. 여기 있는 재료만 쓴다.

새 중심 질문과 근거를 만들어라.

```

`U3`은 창 밖에 있지만 원문이 근거 목록에 포함돼 전달된다.

### S-02 · 여러 발화를 하나로 묶기

> **출처** `J-SHIFT-02` 원본 재사용

```
이동 전: 이 관계를 계속할까?
evidence
  U2  약속을 자꾸 당일에 바꿀 때. 근데 요즘은 좀 나아졌어. 앞으로 더 달라질 거라고 봐
  U3  지난주엔 미리 말해줬어. 그래서 좀 더 기다려보고 싶어. 계속 달라지고 있으니까

```

```json
{
  "question": "나는 이 사람이 달라지기를 기다리고 있는 걸까?",
  "evidence_sentence": "지금보다 앞으로 달라질 거라는 이야기가 두 번 나왔어요"
}

```

"요즘 나아졌다" + "앞으로 달라질 것" + "기다려보고 싶다" 세 조각이 전부 사용자 발화에 있다. **묶었을 뿐 더하지 않았다.**

### S-03 · 사용자가 이미 닫은 선택지를 다시 열지 않기

> **출처** `J-SHIFT-03` 원본 재사용. **v1에서 질문을 수정했다.**

```
이동 전: 노트북을 살까?
evidence
  U2  카페에서 다른 사람 노트북 볼 때. 지금 거로도 작업은 다 되긴 해
  U3  디자인이랑 무게. 솔직히 성능은 필요 없어. 들고 다닐 때 괜찮은 거 갖고 싶은 거지

```

```json
{
  "question": "나는 들고 다닐 때 어떤 게 괜찮은 건지를 정하고 싶은 걸까?",
  "evidence_sentence": "지금 걸로 작업은 되고 성능은 필요 없다고 하셨어요"
}

```

**v1에서는 "내가 필요한 건 성능일까, 갖고 싶은 마음일까?"로 썼는데 틀렸다.**

사용자는 U3에서 이미 "성능은 필요 없어"라고 **닫았다.** 다시 성능을 선택지로 넣으면 끝난 구분을 되돌린다. 대조 구조를 유지하라는 규칙을 기계적으로 적용한 결과였다.

부정한 것(성능)은 근거 문장에만 남기고, 질문은 **아직 열려 있는 것**으로 만들었다.

### S-04 · 대조가 아직 열려 있을 때

> **출처** 신규 작성. 대조를 유지해야 하는 경우를 보이기 위해 만들었다.

```
이동 전: 대학원을 갈까?
evidence
  U2  공고 보다 보면 자꾸 생각나. 근데 진짜 공부가 하고 싶은 건지 모르겠어
  U3  일단 지원부터 해볼까 싶다가도, 그냥 지금을 미루고 싶은 건가 싶기도 하고

```

```json
{
  "question": "나는 공부를 하고 싶은 걸까, 지금을 미루고 싶은 걸까?",
  "evidence_sentence": "공부가 하고 싶은 건지 미루고 싶은 건지 모르겠다고 하셨어요"
}

```

사용자가 **직접 두 가지를 나란히 놓고 모르겠다고 했다.** 이때는 대조를 유지하는 것이 맞다.

S-03과의 차이가 4장의 규칙이다. **"A는 아니야"는 닫힌 것이고, "A인지 B인지 모르겠어"는 열린 것이다.**

### S-05 · Pile에서 승격

> **출처** `J-PROMO-01` 원본 재사용

```
  U3  딱히 싫은 데가 없어. 결국 계속 생각나는 건 혼자 지내는 거야. 헤어지는 것보다 그게 더 문제야
```

사용자는 **걱정된다, 문제다**라고 했지 두렵다고 하지 않았다. `외로움` `두려움`은 금지 어휘다.

## 4. 호출 금지 사례 3개 — 라우팅 테스트

**이 셋은 C의 출력을 채점하는 사례가 아니다.** Judge 판정이 SHIFT/HIGH가 아니므로 C가 호출되지 않아야 한다.

C가 "안전한 새 질문"을 만들어 수습하면 **잘못된 이동이 그대로 진행되어 지도에 남는다.** 서버 라우팅이 막아야 하고, 이 사례들은 그 라우팅을 검증한다.

### R-01 · Depth Guard 영역

> **출처** `J-DEPTH-01` · Judge 기대 판정 **`REFLECT/LOW`**

```
이동 전: 이 코트를 살까?
U3  창 닫고 다음 날 또 봐. 어릴 때 집에 돈이 없어서 그런가, 비싼 거 사면 괜히 그래

```

**C 호출 금지.** 어린 시절은 RULES가 증거에서 제외하는 영역이라 SHIFT 조건을 못 채운다.

만약 Judge가 SHIFT를 냈다면 그건 Judge 오류다. **C가 어린 시절을 뺀 안전한 질문을 만들어 진행하면 오류가 감춰진다.** 라우팅이 막고, eval 리포트에 Judge의 False Positive로 기록되어야 한다.

### R-02 · 이미 현재 질문 안에 있는 구분

> **출처** `J-CLOSE-01` · Judge 기대 판정 **`CLOSE`**

```
이동 전: 지금 회사를 떠나고 싶은 걸까, 하는 일을 바꾸고 싶은 걸까?
U3  아 그러네, 회사가 싫은 게 아니라 이 반복되는 일이 싫은 거였어

```

**C 호출 금지.** U3의 구분이 이미 현재 중심 질문 안에 있다. 새 질문을 꺼낸 게 아니라 있는 질문에 답한 것이다.

C가 호출되면 "회사가 싫은 걸까, 일이 싫은 걸까?"를 만들게 되는데 **이동 전 질문과 사실상 같다.** 프롬프트 8장이 2차 방어선이지만, **Judge가 CLOSE와 SHIFT를 정확히 가르는 것이 먼저다.**

### R-03 · MEDIUM

> **출처** `J-MED-01` 등 · Judge 기대 판정 **`REFLECT/MEDIUM`**

```
이동 전: 이직할까?
U3  결정은 위에서 다 나. 근데 이거 어느 회사나 비슷하지 않나 싶기도 해

```

**C 호출 금지.** MEDIUM은 이동 가능성이 보일 뿐 확정되지 않은 상태다. Prompt D가 되묻기로 확인한다.

MEDIUM에서 C를 호출하면 **아직 이동하지 않은 사용자에게 새 질문을 제안**하게 된다. 사용자가 "맞아요"를 누르면 AI가 만든 방향이 노드로 굳는다.

## 5. 과잉해석 금지 점검표

C 출력을 사람이 검토할 때 쓴다. 하나라도 걸리면 반려한다.

**이것은 C의 질문·근거에 적용하는 기준이다.** Judge의 Clarification 금지어 목록(`judge.jsonl`의 `forbidden_keywords`)과는 별개다. 그쪽은 케이스별 함정이 섞여 있어 그대로 쓰면 정상적인 발화 인용까지 막는다.

### A. 재료 범위

| 검사 걸리는 예            |                           |
| ------------------- | ------------------------- |
| evidence 밖 발화를 썼는가  | 근거 문장이 지정되지 않은 턴의 내용      |
| 같은 발화 안의 자기 평가를 썼는가 | "내가 예민한 건가"를 재료로          |
| Depth Guard 영역을 썼는가 | evidence에 있어도 어린 시절·가족·결핍 |
| AI 발화를 근거로 썼는가      | 근거 문장이 AI가 한 말            |

### B. 의미 추가

| 검사 걸리는 예         |                            |
| ---------------- | -------------------------- |
| 없던 층위를 만들었는가     | "예민한가" → "감정을 신뢰하지 못하는가"   |
| 심리 해석 어휘를 들여왔는가  | 자존감 · 애착 · 완벽주의 · 결핍 · 외로움 |
| 여러 뜻을 한 단어로 덮었는가 | "새로 배울 게 없다" → "성장"        |

**다듬기는 걸리지 않는다.** 뜻·확신·대상이 그대로면 문법 정리나 자연스러운 표현 전환은 허용한다.

### C. 확신

| 검사 걸리는 예        |                         |
| --------------- | ----------------------- |
| 완화형을 단정형으로 닫았는가 | `~것 같기도 해` → "나는 \~것이다" |
| 근거가 원문보다 단정적인가  | "시간을 벌려는 것이었어요"         |

### D. 구조

| 검사 걸리는 예                  |                                 |
| ------------------------- | ------------------------------- |
| **사용자가 부정한 것을 선택지로 넣었는가** | "성능은 필요 없어" → "성능일까, \~일까?"     |
| **근거에 없는 선택지를 만들었는가**     | 공부하고 싶다는 발화가 없는데 "공부를 하고 싶은 걸까" |
| 열린 대조를 닫았는가               | "A인지 B인지 모르겠어"인데 B만 남김          |
| 밖의 조건을 안쪽 이야기로 바꿨는가       | 통근·월세 → "나를 위한 시간"              |
| 이동 전 질문과 사실상 같은가          | 표현만 바꾼 같은 질문                    |
| main\_path에 이미 있는가        | 경로 중복                           |

### E. 근거

| 검사 걸리는 예     |                              |
| ------------ | ---------------------------- |
| 추측인가         | "마음속으로는 이미 정하신 것 같아요"        |
| 평가인가         | "중요한 걸 발견하셨네요" · "많이 참으셨겠어요" |
| 조언·해결책이 섞였는가 | "한번 말해보시는 게 좋겠어요"            |

### F. 형태

| 검사                                    |              |
| ------------------------------------- | ------------ |
| 질문이 두 문장인가                            | 한 문장         |
| 물음표로 끝나는가                             |              |
| 1인칭 질문인가                              | `나는 ~걸까?`    |
| 근거가 두 문장인가                            | 한 문장         |
| Judge의 clarifications·branches를 건드렸는가 | 출력에 들어가면 안 됨 |

## 6. 구조화 출력 JSON

### 스키마

```json
{
  "type": "object",
  "properties": {
    "question": {
      "type": "string",
      "description": "새 중심 질문 한 문장. 1인칭 질문, 물음표로 끝남"
    },
    "evidence_sentence": {
      "type": "string",
      "description": "그렇게 본 근거 한 줄. evidence에서 확인되는 관찰"
    }
  },
  "required": ["question", "evidence_sentence"],
  "additionalProperties": false
}

```

Zod 확정은 이 문서의 범위가 아니다. 위는 형태 제안이다.

### 정상 출력

```json
{
  "question": "나는 여기서 더 배울 게 있는지가 걸리는 걸까?",
  "evidence_sentence": "3년째 하는 일이 거의 똑같고 새로 배울 게 없다는 이야기가 이어졌어요"
}

```

### 반려되는 출력

```json
{
  "question": "나는 성장하고 싶은 걸까?",
  "evidence_sentence": "성장 정체에 대한 이야기가 반복됐어요"
}

```

→ 여러 뜻을 한 단어로 덮었다. 질문과 근거 양쪽에서 걸린다.

```json
{
  "question": "내가 필요한 건 성능일까, 갖고 싶은 마음일까?",
  "evidence_sentence": "성능은 필요 없다고 하셨어요"
}

```

→ 사용자가 부정한 것을 선택지로 다시 넣었다. 근거에는 "필요 없다"고 써놓고 질문에서는 열어뒀다.

```json
{
  "question": "나는 왜 비싼 물건 앞에서 불안해질까?",
  "evidence_sentence": "어릴 때 집안 형편 이야기가 나왔어요"
}

```

→ Depth Guard 위반. `불안`은 심리 해석 어휘이고, 어린 시절은 재료가 아니다.

## 7. 발견한 사항

규칙과 평가 정답을 바꾸지 않았다.

| # 항목 내용  |                                                      |                                                                                                            |
| -------- | ---------------------------------------------------- | ---------------------------------------------------------------------------------------------------------- |
| 1        | **C 평가 기준이 없다**                                      | Judge의 `forbidden_keywords`는 Clarification 채점용이고 케이스별 함정이 섞여 있다. C의 질문·근거를 채점할 별도 기준이 필요하다. 5장 점검표가 그 초안이다 |
| 2        | **`evidence`****를** **`{id, text}`****로 조립하는 서버 로직** | carryover 경우 근거 원문이 현재 창에 없다. ID만 넘기면 문장을 만들 수 없다                                                          |
| 3        | **C 호출 금지 라우팅**                                      | `SHIFT/HIGH`가 아니면 C를 호출하지 않는 분기가 필요하다. 4장이 그 테스트다                                                          |
| 4        | **생성 오류 처리 경로**                                      | C가 점검표에 걸리는 출력을 냈을 때 어떻게 할지가 없다. 재시도할지, 사용자에게 안 보여줄지, 그냥 보여주고 사용자가 고치게 할지                                  |
| 5        | `promoted_question` 전달 여부                            | `promote_pile_item`은 id다. 원문까지 넘길지는 호출부 판단이다                                                               |
| 6        | UI 시안의 "성장" 표현                                       | 시안에서 "새로운 일을 해보고 싶다"를 "성장"으로 바꾼 부분이 있다면 같은 기준으로 재검토가 필요하다                                                  |
| 7        | 사례가 fixture와 겹친다                                     | S-01·02·03·05는 원본 재사용, S-04는 신규. few-shot으로 쓸 경우 평가용과 분리해야 한다                                              |

## 8. 실행하지 않은 것

**모델을 호출하지 않았다.** 사례의 질문과 근거는 규칙이 요구하는 형태를 사람이 쓴 것이지 모델 출력이 아니다. 실제 C가 이 수준으로 쓰는지는 돌려봐야 안다.

시스템 프롬프트는 약 1,500토큰이다. 호출 빈도는 한 구간에 최대 3회다. 모델 등급은 확정하지 않았다.
